# Repository workflow

- Read docs/research-architecture-report.md, docs/implementation-status.md and the scoped vendor evidence before changing an adapter or control.
- Do not infer protocol/register/control semantics from branding, a UI menu, a similar field name, or a public endpoint alone. Missing evidence stays UNKNOWN.
- Default READ ONLY. Never use real credentials, hardware, browser sessions or production writes in automated tests. Simulator fixtures belong only under tests/.
- New commissioned capabilities require exact device/logger/firmware/account/region identity, official evidence, reviewed range/unit/enum, fresh readback and an acceptance record. Do not add wildcard profiles or bypass the command engine.
- Keep native features discoverable with a reason when locked; do not collapse independent export/battery/meter/grid controls into an inaccurate universal action.
- Current user workflow: implement BE, FE and meaningful test code together across the requested scope; do not repeatedly run tests, builds or QA between small implementation batches. Run ruff check, pytest (including authored browser contracts), JavaScript syntax checks and python -m build in the consolidated verification phase, then functional/visual QA. Fix findings and rerun affected checks as needed. Until executed, explicitly mark new code/tests as unverified, not passed or production-ready. A source-inventory command is not a test run.
- Use one controller process. Preserve idempotency, per-device serialization, site isolation and unknown-outcome quarantine.
- Never commit secrets, raw customer payloads, browser cookies, database files or screenshots containing customer identifiers.
- All routes must use the shared shell/sidebar and global static/app.css design system. Do not add per-route stylesheets, inline CSS or duplicate sidebars. Read docs/ui-design-system.md before UI changes; keep docs/mockup-coverage.md honest about BE, FE, incomplete workflows and hardware acceptance.

## Required public-source research for unverified ecosystems

- Before extending an unverified vendor, OEM, logger or model profile, actively research current public web sources. Search the manufacturer's public API/developer portal, manuals/protocol documents and public source repositories maintained by developers building comparable monitoring, O&M, EMS, Home Assistant or device-integration applications. Do not stop at the vendor catalogue, a missing public API or waiting for the user's login.
- Inspect relevant upstream implementation files, protocol definitions, tests/fixtures, release notes and issue discussions. Prefer original manufacturer and project-maintainer sources; record where a community finding conflicts with official documentation. If no suitable source is found, record what was searched and the unresolved contract instead of asserting support or silently omitting the ecosystem.
- Public API clients, compatible OSS libraries and reusable source are authorized development inputs. Reuse or adapt code when its actual license permits the intended use. Public visibility alone is not a copying license. Record the repository URL, exact commit/tag and source paths, license and applicable obligations; preserve copyright/license notices and update THIRD_PARTY_NOTICES.md and dependency pins. For unclear or incompatible licensing, use a suitable alternative or independently implement documented behavior without copying restricted source; continue independent work rather than stopping the entire product.
- Maintain source provenance and applicability in docs/vendor-source-audit.md, docs/evidence/source-registry.json and the packaged registry when relevant. Record access date, evidence grade, exact model/OEM/logger/firmware/platform, authentication and region assumptions, read/write/readback coverage, known limitations and which implementation derives from which source. Separate verified facts, maintainer claims, community observations and hypotheses.
- Reverse engineering for interoperability may use public code/documentation and the user's authorized accounts/devices. Keep observation within that scope; do not bypass authentication, MFA, access controls or discover unrelated customer data. Store sanitized contracts/fixtures, not session cookies, secrets or raw customer payloads. A user's logged-in browser permits the requested inspection, not unrequested physical writes.
- Translate researched behavior inside the adapter or exact model/profile. Keep core vendor-neutral. Distinguish brand from OEM, monitoring platform and logger, especially Bluesun/SmartESS/Eybond/SOLARMAN variants. Adding a logo, a form, a dependency or a community decoder is not full ecosystem support.
- Write contract tests and simulator cases alongside integration code for authentication/renewal, discovery, normalization, errors/quotas, capabilities, alarms and supported control/readback. Follow the consolidated execution timing above. Community research or passing fixtures does not itself grant commissioned hardware capability; preserve exact identity, evidence, permissions, acceptance and readback gates.
- After each coherent implementation batch, update docs/mockup-coverage.md: the 26-screen BE/FE inventory, canonical sidebar/tab responsibilities, the separate estimate → existing code → unbuilt scope → completion criteria table, and reproducible actual BE/FE/test counts via scripts/measure_code.py --update-doc. Do not describe unfinished engineering as merely waiting for credentials, use LOC as completion percentage or add filler to meet an estimate.
